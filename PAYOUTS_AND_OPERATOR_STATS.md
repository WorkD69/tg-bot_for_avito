# Operator Stats & Payouts

## Как устроена модель

### Таблица `operator_earnings`

Одна строка на каждую завершённую заявку. Создаётся автоматически при переходе заявки в статус `completed`.

| Поле | Тип | Описание |
|------|-----|---------|
| `order_id` | FK (unique) | Связь с заявкой — один earning на заявку |
| `operator_id` | FK | Оператор, выполнивший заявку |
| `gross_amount` | Decimal | Что заплатил клиент (= `order.payment_amount` в момент завершения) |
| `operator_share` | Decimal | Что получает оператор (`gross * payout_percent / 100`) |
| `payout_percent` | Decimal | Процент выплаты на момент расчёта (хранится для аудита — не пересчитывается при смене конфига) |
| `status` | Enum | `pending` / `paid` / `excluded` / `adjusted` |
| `paid_at` | DateTime | Когда отмечено как выплачено |
| `paid_by_id` | FK | Кто отметил выплату (admin user.id) |
| `note` | Text | Комментарий: причина исключения / корректировки / примечание к выплате |

### Статусы выплат

| Статус | Иконка | Описание |
|--------|--------|---------|
| `pending` | ⏳ | Ожидает выплаты (дефолт) |
| `paid` | ✅ | Выплачено оператору |
| `excluded` | 🚫 | Исключено из выплаты (спор, возврат, решение админа) |
| `adjusted` | ✏️ | Сумма скорректирована вручную |

## Как считаются выплаты

### Формула

```
operator_share = gross_amount × payout_percent / 100
```

Округление — ROUND_HALF_UP до 2 знаков после запятой.

### Конфигурация

В `.env`:
```env
OPERATOR_PAYOUT_PERCENT=80.0   # процент оператора от суммы заказа (дефолт: 80%)
```

Процент хранится в строке earning в момент создания — можно менять конфиг без пересчёта старых записей.

### Пример

Клиент заплатил 2000 ₽, процент оператора 80%:
- `gross_amount = 2000.00`
- `operator_share = 1600.00`
- Платформа забирает: 400 ₽

---

## Когда создаётся earning

1. **Оператор загрузил решение `/done`** — автоматическое завершение (`solution_done` handler в `notes.py`)
2. **Админ принудительно завершил `/completeorder {id}`** — (`cmd_complete_order` в `commands.py`)

Оба случая: `EarningRepo.create_for_order()` — идемпотентно, двойное создание невозможно.

Earning создаётся только если у заявки есть `payment_amount` и `operator_id`.

## Команды администратора

### `/operatorstats` — статистика операторов

```
/operatorstats                    — сводка по всем операторам
/operatorstats @vasya             — детали по одному оператору (всё время)
/operatorstats @vasya 7d          — последние 7 дней
/operatorstats @vasya 30d         — последние 30 дней
/operatorstats 123456789          — по telegram_id
```

**Показывает:**
- Активных заявок сейчас
- Завершённых заявок
- Средний чек
- Общая выручка (gross)
- К выплате оператору (total_share)
- Из них: выплачено / pending
- Список последних 15 заявок с суммами и статусом

### `/payouts` — pending выплаты

```
/payouts                — все операторы с pending выплатами
/payouts @vasya         — pending выплаты конкретного оператора
/payouts 123456789      — то же по telegram_id
```

**Показывает список заявок с суммами и итоговую сумму к выплате.**
В конце выводит команду `/markpaid @op` для быстрой оплаты.

### `/markpaid` — отметить выплату как произведённую

```
/markpaid @vasya
/markpaid @vasya Перевод на карту *1234 05.04.2026
/markpaid 123456789 USDT tx:abc123
```

Помечает **все pending earnings** оператора как `paid`. Записывает:
- `paid_at = now()`
- `paid_by_id = admin.id` (кто выполнил команду)
- `note = примечание` (если указано)

### `/excludeearning` — исключить заявку из выплат

```
/excludeearning 42
/excludeearning 42 Клиент оформил возврат
```

Переводит earning заявки №42 в статус `excluded`. Earning остаётся в БД (аудит), но не входит в pending сумму.

**Используйте при:**
- Споре по заявке
- Возврате средств клиенту
- Решении о штрафе оператора

### `/adjustearning` — скорректировать сумму выплаты

```
/adjustearning 42 1200
/adjustearning 42 1200 Штраф за задержку — вместо 1600 выплачиваем 1200
```

Устанавливает `operator_share = 1200`, статус → `adjusted`. `gross_amount` не меняется — для аудита.

## Спорные и скорректированные заявки

### Правило: спорные заявки НЕ исключаются автоматически

Система не имеет понятия "спор" как статус. Если по заявке возник спор:
1. Не завершайте заявку (`/completeorder`) до урегулирования
2. Если уже завершена и earning создан — используйте `/excludeearning` или `/adjustearning`

### Порядок работы со спором

```
# Вариант А: полное исключение
/excludeearning 42 Спор: клиент не получил решение

# Вариант Б: частичная выплата
/adjustearning 42 500 Компромисс: 500 вместо 1600 после спора
```

После исключения/корректировки статус earning'а остаётся `excluded`/`adjusted` навсегда — история сохраняется.

## Как делать выплаты: пошаговый процесс

### Ежемесячная/еженедельная выплата

```
1. Посмотреть все pending:
   /payouts

2. Для каждого оператора — детали:
   /payouts @vasya

3. Перевести деньги (банк / USDT / другой способ)

4. Отметить как выплачено:
   /markpaid @vasya Сбер *1234, 2000 ₽, 01.04.2026

5. Проверить что pending = 0:
   /operatorstats @vasya
```

### Экспорт данных

Команды выводят текст в Telegram. Для CSV-экспорта — прямой SQL-запрос:

```sql
SELECT
    oe.id,
    u.full_name AS operator,
    u.telegram_id,
    oe.order_id,
    oe.gross_amount,
    oe.operator_share,
    oe.payout_percent,
    oe.status,
    oe.paid_at,
    oe.note,
    oe.created_at
FROM operator_earnings oe
JOIN users u ON u.id = oe.operator_id
ORDER BY oe.created_at DESC;
```

## Что НЕ реализовано (намеренно)

| Возможность | Причина отсутствия |
|------------|-------------------|
| Батчи выплат (один batch = одна транзакция) | Избыточно для текущего масштаба — `/markpaid` достаточно |
| Автоматические уведомления операторам о выплате | Требует доработки по запросу |
| Период выплаты (дата начала / конца) | Можно добавить при росте нагрузки |
| Ставка НДС / налоги | Не входит в MVP |
| Мульти-валюта | Не нужно (рубли) |
